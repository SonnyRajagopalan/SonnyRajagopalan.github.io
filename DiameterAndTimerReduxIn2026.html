Reviving a 2012 Telecom Stack: What I Learned Fixing a Diameter Protocol Implementation

I recently spent time with a C++ Diameter protocol implementation I wrote back in 2012 for an embedded Linux telecom environment (see a small piece of it in here). The codebase was built under serious constraints: no C++11 threading, no STL containers in shared memory, no heap allocation for hot-path objects. Just raw POSIX: fork(), shm_open, sem_wait, and a handwritten binary min-heap.

It was a time capsule of embedded systems design.

The Architecture

The Diameter protocol (RFC 3588) is the AAA framework behind LTE/5G core networks. It needs reliable timer scheduling — watchdog keepalives, request retransmission timers, reconnection backoffs. Back in 2012, I chose an unusual approach: the timer scheduler runs in a forked child process, not a thread (see this SO thread for when I got some pushback from the community about my design choices). Shared memory connects parent and child. A POSIX message queue delivers expiry notifications.

This buys fault isolation (a buggy timer scheduler kills only the child) and worked around broken pthreads in some 2012 toolchains. But it introduces real complexity: named semaphores for cross-process locking, shared-memory object pools, and careful initialization ordering between parent and child.

What I Fixed

I swear this worked back in 2012-I had valgrind-ed the whole thing! But, in 2026, the timer heap had a race condition. The TimerTask child and the parent's message queue thread both modified the min-heap array and its element counter without synchronization. Under load — 500 timers firing 10 times each — only 900 of 5,000 expected fires would complete, with jitter as bad as -12,000ms. Adding a cross-process heap semaphore fixed it: 10,000/10,000 fires, zero lost, zero early.

I also fixed a number of readability things--I had used couts a lot--cleaned things up. I also had a number of tests that made sense back in 2012 as a project I learned a lot from--cleaned those not so useful tests now

I used opencode.ai (LLM: Deepseek V4 Flash Free, provider opencode) extensively with codebase-memory-mcp and also introduced MCP/Server memory later (more on this below). It was my first project with opencode and I think I like using it a lot more than pi.dev or cursor cli.

What I Built

I turned the repo into a study on timer management with:

  • A timer accuracy stress tool that measures microsecond jitter with statistical reporting (min/max/mean/stddev/p50/p90/p95/p99) and direction breakdown (early/on-time/late).
  • Architecture Decision Records (ADRs) — five documents explaining why fork over threads, why a min-heap over a timer wheel, why shared-memory pools, why POSIX message queues, and why the State pattern for the peer FSM.
  • Mermaid diagrams — sequence diagrams for the timer fire lifecycle, class diagrams for the shared-memory objects, and a state machine diagram for the Diameter peer FSM.
  • A Dockerfile for reproducible builds (Ubuntu 22.04, multi-stage).
  • Unit tests — a MemoryPool test (22 tests covering allocation, index round-trip, exhaustion, and cross-process fork access) and an FSM state test (25 tests covering state names, singleton identity, event strings, and peer state values).

The MCP Integration

This was also an experiment in using AI coding harnesses. The repo integrates with two MCP toolkits:

codebase-memory indexes the entire codebase into a Neo4j knowledge graph. You can run queries like search_graph(name_pattern=".*Timer.*") to find all timer-related classes, or trace_path(function_name="Timer::scheduleOneShotAtTimeout") to follow the call chain from scheduling to heap insertion to cross-process notification.

conversational-memory logs test sessions as knowledge graph entities. After python test/runner.py --all, results are stored with timestamps, pass/fail counts, and jitter statistics. You can query the history later: search_nodes(query="test session").

The TUTORIAL.md walks through each tool step by step.

What This Taught Me

The 2012 design isn't wrong — it was right for its constraints. The fork+shared memory pattern gives genuine fault isolation that threads cannot match. The binary min-heap in contiguous shared memory is simpler and more debuggable than a timer wheel when you're managing ≤1024 timers. The memory pools eliminate heap fragmentation in a process meant to run for months.

But the modern alternatives are compelling too: timerfd_create() + epoll replaces the entire fork+shm+mq machinery with a single file descriptor. io_uring can submit timer requests directly to the kernel. A thread-backed std::priority_queue with std::condition_variable replaces 500 lines of POSIX IPC with 50 lines of standard library.

The repo is at github.com/SonnyRajagopalan/ABasicDiameterImplementationInCPP — I hope it serves as a useful study for anyone interested in timer management, embedded systems architecture, or AI-assisted code exploration.
